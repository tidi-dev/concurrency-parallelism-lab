# 3. Experiment — Sequential

Simulate async tasks such as:

async function task() {
    await sleep(1000)
}

Execute:

await task()
await task()
await task()

Expected timeline:

Task 1 █████
Task 2      █████
Task 3           █████

Total:

~3 seconds

Explain:

Only one task is being awaited before the next starts.

---

# 4. Experiment — Concurrency

Run the same simulated I/O tasks using:

await Promise.all([
    task(),
    task(),
    task()
])

Expected:

Task 1 █████
Task 2 █████
Task 3 █████

Total:

~1 second

Explain clearly:

These tasks are CONCURRENT.

Do NOT say they are necessarily running JavaScript simultaneously on multiple CPU cores.

The tasks overlap because JavaScript starts them and waits for asynchronous operations to complete.

Teach:

CONCURRENCY ≠ PARALLELISM

---

# 5. Experiment — Main-thread blocking

Create a CPU-heavy JavaScript function.

For example:

calculatePrimes(...)

or another deterministic CPU loop.

Run several CPU-heavy tasks on the main JavaScript thread.

Show that the UI becomes temporarily unresponsive.

Add a small animation such as:

● moving continuously

or:

UI heartbeat: 1 2 3 4 ...

When CPU-heavy JavaScript blocks the main thread, the animation should visibly freeze.

This is intentional and educational.

Explain:

JavaScript cannot process UI updates while synchronous CPU work is blocking the main thread.

Also demonstrate that:

Promise.all([
    cpuTask(),
    cpuTask(),
    cpuTask()
])

does NOT magically make synchronous CPU work parallel.

This misconception is extremely important to address.

# 6. Experiment — Real parallelism

Implement the same CPU-heavy workload using browser Web Workers.

Architecture:

Browser Main Thread
       │
       ├── Worker 1 → CPU Task 1
       ├── Worker 2 → CPU Task 2
       └── Worker 3 → CPU Task 3

Each worker should report:

workerId
taskId
startedAt
finishedAt
duration

Visualize:

Worker 1 █████████
Worker 2 █████████
Worker 3 █████████

The UI heartbeat should continue running while workers perform CPU work.

Explain:

This is actual parallel-capable execution.

Multiple workers may execute on different CPU cores.

Use:

navigator.hardwareConcurrency

to display the browser's reported logical processor count.

For example:

Logical processors reported by browser: 8

Allow:

Workers:

[1] [2] [4] [8]

Then let me compare execution time.

Explain why:

MORE WORKERS != ALWAYS FASTER

because of:

- available CPU cores
- scheduling
- worker overhead
- communication overhead
- contention

# 11. Important misconceptions

The demo should explicitly teach that these statements are wrong or incomplete:

"Concurrency = parallelism"

"Promise.all makes JavaScript parallel"

"async/await creates threads"

"100 promises = 100 threads"

"Web Workers are the same as promises"

"More workers always means faster"

"async makes CPU-heavy work faster"

Use the experiments to demonstrate WHY.
